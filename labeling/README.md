# LLM 라벨링 파이프라인

게임 상태에 매크로 행동(레벨업 / 리롤 / 저축 / 유지) 라벨을 붙여, 상태 → 행동 분류기를
학습시키려 했던 시도의 기록.

```
sample_states.py   상태 합성 (텍스트 + 수치 피처)
label_states.py    LLM(Solar)으로 행동 라벨 생성
train_classifier.py  피처 → 행동 분류기 학습
```

## 무엇이 문제였나

라벨 300개를 뽑아 분류기를 학습시켰더니 검증 정확도가 90% 근처로 나왔다.
그런데 예측 분포를 보니 거의 한 클래스만 찍고 있었다.

| 시도 | 프롬프트/데이터 | 라벨 분포 | 검증 정확도 | 실제로 학습된 것 |
|---|---|---|---|---|
| 1차 | 기본 프롬프트 | level_up 91% | 90% | 다수 클래스만 예측 |
| 2차 | "레벨업 남발하지 마라" 추가<br>+ 저축/리롤 유리한 프로필 비중 확대 | save_econ 90% | 88% | 다수 클래스만 예측 |

프롬프트를 반대 방향으로 밀자 라벨도 정확히 반대로 쏠렸다.
쏠린 방향만 바뀌고 편향 자체는 그대로였다.

라벨의 `reasoning` 필드를 읽어보면 더 분명하다. "체력이 안전하고 레벨업하면 4코스트를
열 수 있다"고 써놓고 `primary_action`은 `save_econ`인 경우가 적지 않았다.
근거와 결론이 일치하지 않는다.

## 원인과 대응

모델이 게임을 몰라서가 아니라, **상태마다 행동 하나만 고르게 한 과제 설계** 때문이었다.
실제 판단은 "체력이 이러면 리롤, 골드가 저러면 레벨"처럼 조건부인데, 단일 라벨은
그 분기 구조를 담지 못한다. 그래서 모델은 프롬프트가 암시하는 쪽으로 전체를 밀어버린다.

같은 지식을 조건부 규칙으로 옮기니 행동이 상태에 따라 갈렸다
([../fullgame/macro_rules.py](../fullgame/macro_rules.py)의 `decide_conditional`).
같은 상태 300개에 이 규칙을 적용했을 때:

```
save 77% / roll 23%   - 발동 조건별로 보면
  이자 회복        182
  이미 충분히 강함   49
  체력/연패 안정화   48
  이자 위 초과분 리롤 20
```

한 행동으로 무너지지 않고, 서로 다른 조건이 서로 다른 행동을 만들어냈다.

## 남은 한계

- 조건부 규칙은 사람이 쓴 것이고, LLM이 생성하도록 만들지는 않았다.
- 이 방향 대신 보상을 요인별로 분해해 학습시키는 쪽([../hra](../hra))으로 옮겼다.
