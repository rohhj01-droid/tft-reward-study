# TFT 강화학습: 보상 설계와 학습-목표 환경의 괴리

오토배틀러(TFT Set 4)에서 강화학습 에이전트의 보상을 어떻게 설계하느냐가 학습된 정책을
어떻게 바꾸는지 실험한 기록이다. "TFT를 잘하는 봇"을 만드는 게 목표는 아니었다.
학습 신호를 바꿔가며 그 영향을 재고 검증하는 쪽이 목표였다.

결과부터 적으면, 보상을 요인별로 쪼개 학습시킨 에이전트는 아무도 알려주지 않은 경제
전략(이자를 유지하면서 초과 골드로만 리롤하는 slow-roll)을 스스로 찾아냈다. 요인
가중치를 바꿔 5시드씩 반복해 보니 단일 목표보다 두 요인을 섞은 쪽이 더 좋았다.
그런데 그렇게 학습한 정책을 실제 게임에 넣으니 오히려 등수가 나빠졌다(-0.84 ± 0.25).
학습에 쓴 지표가 시너지와 유닛 수를 세지 않아서였다.

측정값 전체는 [results/README.md](results/README.md)에 있다.

## 배경

TFT는 매 라운드 제한된 골드를 유닛 구매, 레벨업, 상점 리롤에 나눠 쓰는 게임이다.
보상(등수)은 게임이 끝나야 확정되고, 그 사이 수백 번의 행동 중 무엇이 기여했는지
알기 어렵다. 8인 자가대전이라 상대에 따라 최적 행동도 달라진다.

공개된 MuZero 기반 에이전트([silverlight6/TFTMuZeroAgent](https://github.com/silverlight6/TFTMuZeroAgent))
위에서 학습을 돌려봤는데 유닛 성장이 계속 정체됐다. 파고들수록 "모델을 더 오래 돌리면
되는 문제"가 아니라 무엇을 보상으로 주고 있는지의 문제로 보였다. 그래서 보상 설계
자체를 주제로 잡았다.

## 저장소 구성

```
set4.py             Set 4 상수 (상점 확률, 유닛 풀, 레벨 비용, 트레잇)
hra/                다중 보상 학습기
  env.py              경제 환경 (전투 없음)
  env_battle.py       전투를 연결한 환경
  model.py            요인별 헤드를 가진 Q 네트워크
  train.py            학습 루프
  train_battle.py     승패까지 보상에 넣은 학습
  sweep.py            가중치 x 시드 스윕
analysis/           시뮬레이션 분석
  battle.py           전투 하네스 (보드 대 보드)
  star_value.py       별 등급 vs 유닛 수
  roll_odds.py        레벨별 리롤 골드 효율
  lever_test.py       스탯 너프의 통계적 유의성
  synergy.py          board_value 가 놓치는 요인
  comp_tiers.py       조합 라운드로빈 티어
fullgame/           완전한 게임에서의 검증
  macro_rules.py      조건부 매크로 규칙
  policy.py           풀게임용 정책
  ab_test.py          같은 게임 안에서의 A/B
  board_stars.py      기본 봇 최종 보드 측정
labeling/           LLM 라벨링 파이프라인 (README 별도)
results/            측정 기록
```

`hra/env.py`, `hra/train.py`, `hra/sweep.py`, `analysis/roll_odds.py`,
`fullgame/macro_rules.py` 는 시뮬레이터 없이 그대로 돌아간다. 나머지는 시뮬레이터
저장소가 필요하다(맨 아래).

## 출발점: 기본 봇은 무엇을 못 하는가

시뮬레이터에 내장된 규칙 기반 봇이 게임을 끝낼 때의 보드를 세어봤다.

```
평균 레벨 8.00
1성 4.58 (57%)   2성 3.02 (38%)   3성 0.41 (5%)
```

레벨은 항상 최대까지 올라가는데 보드의 절반 이상이 1성이다. 같은 유닛을 3장 모으면
2성이 되는 게임에서 이 봇은 유닛을 모으지 못하고 있었다.

## 별을 올리는 게 실제로 이득인가

위 관찰이 실제로 손해인지부터 확인했다. 경제와 의사결정을 다 빼고 보드끼리만 붙였다.

| 비교 | 승률 |
|---|---|
| 미러 매치 (2성 vs 2성) | 51.6% |
| 같은 조합 2성 vs 1성 | 96.9% |
| 6유닛 2성 vs 8유닛 1성 | 82.3% |

미러가 50% 근처라 하네스 자체에 진영 유리는 없다. 유닛을 두 개 덜 쓰더라도 별을 올린
쪽이 이긴다. 레버는 레벨이 아니라 유닛 성장이다.

## LLM으로 방향을 주려던 시도

에이전트에게 어떻게 두어야 하는지 알려주려고, 게임 상태에 LLM으로 매크로 행동 라벨을
붙이고 분류기를 학습시켰다. 검증 정확도가 90%였는데 예측 분포를 보니 거의 한 클래스만
찍고 있었다.

| 시도 | 라벨 분포 | 정확도 |
|---|---|---|
| 1차 | level_up 91% | 90% |
| 2차 (프롬프트에 반대 방향 지시 추가) | save_econ 90% | 88% |

프롬프트를 반대로 밀자 쏠림 방향만 정확히 뒤집혔다. 라벨의 근거 필드를 읽어보면
"레벨업하면 4코스트를 열 수 있다"고 써놓고 행동은 `save_econ`인 경우도 있었다.

모델이 게임을 몰라서가 아니라 상태마다 행동 하나만 고르게 한 과제 설계 때문이었다.
실제 판단은 "체력이 이러면 리롤, 골드가 저러면 레벨"처럼 조건부인데 단일 라벨은 그
구조를 담지 못한다. 같은 지식을 조건부 규칙으로 옮기자 행동이 상태에 따라 갈렸다.
자세한 건 [labeling/README.md](labeling/README.md).

## 보상을 요인별로 나누기

여기서 접근을 바꿨다. 사람이 정답 행동을 지정하는 대신 보상을 요인으로 쪼개고 학습기가
스스로 찾게 하는 방식(Hybrid Reward Architecture)이다.

```
board : 보드 강도 증가분   (Σ 코스트 x 3^(별-1))
econ  : 그 라운드의 이자
win   : 전투 승패          (train_battle 에서 추가)
```

요인마다 독립된 Q 헤드를 두고, 행동을 고를 때만 가중합한다.

```
Q_total(s, a) = Σ_i  w_i * Q_i(s, a)
```

이렇게 하면 두 가지가 생긴다. 각 요인이 매 라운드 측정되므로 학습 신호가 밀집해지고,
어떤 요인이 그 행동을 밀었는지 헤드별 Q값으로 확인할 수 있다(`model.explain`).

전투를 매번 돌리면 느려서, 먼저 전투를 board_value 로 근사한 경제 환경(`hra/env.py`)에서
학습시켰다. 상점 확률, 유닛 풀, 레벨업 비용, 패시브 경험치는 시뮬레이터 값을 그대로 썼다.

| 정책 | board_value |
|---|---|
| 항상 저축 | 0.0 |
| fast-8 (레벨 우선) | 2.7 |
| 무작위 | 16.6 |
| slow-roll (수동 설계) | 35.7 |
| **학습된 정책** | **36.5** |

학습된 정책을 레벨/골드 격자로 찍어보면 골드가 이자 구간 위일 때만 리롤하고 그 아래에서는
저축한다. 이자를 깨지 않는 리롤이라는 규칙을 따로 넣지 않았는데 같은 결론에 도달했다.

전투 승패를 요인에 추가해 다시 학습시킨 경우에도 벤치마크 상대 승률 83~85%로 수동 최적
정책(83%)과 같은 수준이었다.

## 가중치가 정책을 만든다

요인이 여러 개면 어떤 비율로 섞을지가 새로운 설계 변수가 된다. 단일 실행으로는 순위가
실행마다 뒤집혀서 가중치 조합마다 5개 시드로 반복했다.

| board : econ | board_value | ROLL 비율 |
|---|---|---|
| 1 : 0.0 | 33.9 ± 0.3 | 61% |
| 1 : 0.3 | **35.6 ± 0.2** | 64% |
| 1 : 0.6 | 35.0 ± 0.7 | 67% |
| 1 : 1.0 | 31.5 ± 2.7 | 59% |

보드만 보상하는 단일 목표가 최적이 아니었다. 경제를 조금 섞은 쪽이 더 높고 두 구간은
표준편차 기준으로 겹치지 않는다. 이자를 유지해야 결국 더 많이 굴릴 수 있는데, board 만
보는 헤드는 그 연결을 잘 학습하지 못하는 것 같다.

경제 가중치를 과하게 키우면 성능이 떨어지는 동시에 시드 간 편차가 0.3에서 2.7로 커진다.
평균값보다 이 불안정성이 더 문제다.

ROLL 비율은 시드마다 크게 흔들리는데 board_value 는 안정적이다. 성능이 같은 서로 다른
정책이 여럿 있다는 뜻이라, 정책 하나만 보고 해석하면 안 된다.

## 실제 게임에 넣으니 무너졌다

여기까지는 전부 단순화된 환경 안에서의 결과다. 이 정책을 완전한 게임(8인, 실제 전투)에
넣고 같은 게임 안에서 절반은 새 정책, 절반은 기본 봇으로 40게임을 돌렸다.

| 지표 | 새 정책 | 기본 봇 |
|---|---|---|
| 평균 등수 | 4.92 | 4.08 |
| 평균 레벨 | 6.09 | 7.99 |
| 1성 유닛 | 2.22 | 5.44 |
| 2성 유닛 | 3.85 | 2.52 |

등수 차이 **-0.84 ± 0.25 (SEM)**. 유의하게 나빴다.

의도한 대로 움직이기는 했다. 레벨을 낮게 유지하고 2성을 더 많이 만들었다. 그런데 그렇게
만든 보드가 실제 전투에서 졌다.

원인은 학습에 쓴 지표에 있었다. `board_value` 는 유닛의 코스트와 별만 세고 트레잇 시너지와
유닛 수를 세지 않는다. 학습기 입장에서는 "6유닛 2성"이 최적이었지만 실제 전투에서는
유닛 수와 시너지가 승패를 갈랐다.

같은 정책으로 조합만 바꿔 재보면 분명해진다.

| 조합 | 시너지 단계 | board_value | 승률 |
|---|---|---|---|
| 1코 비시너지 | 4 | 19.9 | 19% |
| 2~3코 (Warlord) | 4 | **41.2** | 62% |
| 4~5코 고밸류 | 6 | 15.8 | 1% |
| 1~3코 Duelist/Divine | 6 | 34.9 | **83%** |

board_value 1위 조합이 승률 1위가 아니다. 지표를 최적화한 결과가 목표에서 멀어지는,
전형적인 대리 지표 문제였다.

레벨 목표를 실제 게임 기준으로 올려 유닛 수를 확보하게 하자 등수 차이가
**-0.06 ± 0.24** 로 사라졌다(2성 3.66 vs 2.44). 더 적은 유닛으로 더 높은 별을 유지하면서
기본 봇과 같은 성적을 낸다.

## 삽질 기록

**작은 표본은 순위를 뒤집는다.** 챔피언 스탯을 하나씩 깎아 승률 변화를 보는 실험을 처음에
N=15로 돌렸고, 공격속도가 가장 큰 레버라는 결론을 얻었다. N=60으로 다시 재고 95% 신뢰구간을
그려보니 공격속도는 기준 구간과 겹쳐 유의하지 않았고 실제 레버는 공격력이었다. 이후 모든
비교에 신뢰구간과 다중 시드를 붙였다. 풀게임 A/B에서도 40게임에서 유의해 보이던 차이가
60게임에서 사라진 적이 있다.

**코드가 의도대로 실행되는지부터 확인해야 한다.** 풀게임에 매크로 판단을 끼워넣었는데 결과가
기본 봇과 똑같이 나왔다. 판단 함수의 호출 횟수를 세어보니 0이었다. 기본 봇의 정책이 우선순위
캐스케이드로 되어 있어서, 앞쪽 단계가 매 턴 액션을 반환하고 뒤쪽 매크로 판단까지 도달하지
못했다. 게다가 이전 실험에서 만들어 둔 설정 파일이 남아 있어서 모든 에이전트의 행동을
고정시키고 있었다. 두 문제를 찾기 전까지의 A/B 결과는 전부 무의미했다. 계측을 처음부터
넣었으면 며칠은 아꼈을 것이다. 그래서 [fullgame/policy.py](fullgame/policy.py)는 훅을
끼워넣는 대신 각 단계가 "할 일이 있을 때만" 발동하도록 정책을 다시 썼다.

## 한계

- 목표가 "이기는 에이전트"는 아니었고, 실제로도 기본 봇과 동등한 수준까지다. 더 밀어붙이려면
  시너지를 보상에 직접 넣고 재학습해야 하는데 거기까지는 하지 않았다.
- 경제 환경은 전투를 board_value 로 근사한 단순화 모델이다. 아이템, 포지셔닝, 상대 플레이어와의
  유닛 경합은 들어있지 않다.
- 조합은 고정해 두고 경제 결정만 학습시켰다. 어떤 조합으로 갈지는 학습 대상이 아니다.
- 시뮬레이터의 챔피언 코스트가 실제 Set 4와 일부 다르다. 여기서 나온 밸런스 결론은 시뮬레이터
  안에서만 유효하고 실제 게임에 그대로 옮길 수 없다.

## 실행

시뮬레이터 없이 도는 부분:

```bash
pip install torch numpy

python -m hra.env                 # 수동 정책들의 board_value 비교
python -m hra.train               # 다중 보상 학습
python -m hra.sweep --seeds 5     # 가중치 스윕 -> results/weight_sweep.csv
python -m analysis.roll_odds      # 레벨별 리롤 효율
python -m fullgame.macro_rules    # 조건부 규칙이 상태에 따라 갈리는지 확인
```

`analysis/`, `fullgame/`, `hra/env_battle.py` 는
[silverlight6/TFTMuZeroAgent](https://github.com/silverlight6/TFTMuZeroAgent) 를 받아
`Simulator` 패키지가 import 가능한 경로에 두고 실행한다.

```bash
python -m analysis.star_value
python -m analysis.synergy
python -m fullgame.board_stars 8
python -m fullgame.ab_test 40
python -m hra.train_battle
```

## 참고

시뮬레이터는 [silverlight6/TFTMuZeroAgent](https://github.com/silverlight6/TFTMuZeroAgent)
(Avadaa의 TFT Set 4 시뮬레이터 기반)를 썼다. 전투 엔진과 게임 규칙은 그 저장소의 것이고,
여기에는 그 위에서 돌린 분석/학습 코드만 담았다. 시뮬레이터에 패치 시스템(10.20~10.24)을
추가하고 실험한 기록은 별도 포크에 있다.

다중 보상 구조는 van Seijen et al., *Hybrid Reward Architecture for Reinforcement Learning*
(2017) 의 아이디어를 이 문제에 맞게 단순화한 것이다.
